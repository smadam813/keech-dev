**Most dev containers trust the network by default. This one does not.** Every outbound connection is blocked unless it is explicitly allowed. The firewall drops traffic to the entire internet, then punches narrow holes for exactly the services a .NET developer needs: GitHub, NuGet, npm, Anthropic, Google, and VS Code marketplace. Nothing else gets through.

I built this because AI coding tools change the threat model of a development environment. Claude Code and Gemini CLI can execute arbitrary shell commands, install packages, and make network requests. That is what makes them powerful. It is also what makes an unrestricted container a liability. This dev container gives AI tools full autonomy inside a network sandbox, so they can do their job without having access to anything they should not.

## The Firewall Sandbox

The standout feature is an iptables firewall that runs on every container start. The default policy is DROP on all chains: INPUT, FORWARD, and OUTPUT. If a destination is not on the allowlist, the connection is rejected immediately.

The allowlist is not a static list of IPs. **GitHub and Google publish their IP ranges through APIs**, and the firewall fetches them dynamically at startup:

```bash
# Fetch GitHub meta information and aggregate + add their IP ranges
gh_ranges=$(curl -s https://api.github.com/meta)
while read -r cidr; do
    ipset add allowed-domains "$cidr" -exist
done < <(echo "$gh_ranges" | jq -r '(.web + .api + .git)[]' | aggregate -q)

# Fetch Google IP ranges (covers all *.googleapis.com and *.google.com)
google_ranges=$(curl -s https://www.gstatic.com/ipranges/goog.json)
while read -r cidr; do
    ipset add allowed-domains "$cidr" -exist
done < <(echo "$google_ranges" | jq -r '.prefixes[].ipv4Prefix // empty' | aggregate -q)
```

GitHub's `/meta` endpoint returns CIDR ranges for their web, API, and git services. Google publishes their ranges in a JSON file at gstatic.com. Both get piped through `aggregate` to consolidate overlapping ranges, then loaded into an `ipset` with `hash:net` for efficient CIDR matching. This is faster than individual iptables rules because the kernel does a single hash lookup instead of walking a rule chain.

**For services that do not publish IP ranges**, the script resolves domains to IPs at startup using DNS:

```bash
for domain in \
    "registry.npmjs.org" \
    "api.anthropic.com" \
    "claude.ai" \
    "api.nuget.org" \
    "volta.sh" \
    "marketplace.visualstudio.com"; do
    ips=$(dig +noall +answer A "$domain" | awk '$4 == "A" {print $5}')
    while read -r ip; do
        ipset add allowed-domains "$ip" -exist
    done < <(echo "$ips")
done
```

Every IP and CIDR range is validated before being added. If a range does not match the expected format, the script exits with an error rather than silently misconfiguring the firewall.

**The script verifies itself on every run.** After all rules are applied, it tests that `example.com` is unreachable (confirming the DROP policy works) and that `api.github.com` is reachable (confirming the allowlist works). If either check fails, the container startup fails:

```bash
if curl --connect-timeout 5 https://example.com >/dev/null 2>&1; then
    echo "ERROR: Firewall verification failed - was able to reach https://example.com"
    exit 1
fi

if ! curl --connect-timeout 5 https://api.github.com/zen >/dev/null 2>&1; then
    echo "ERROR: Firewall verification failed - unable to reach https://api.github.com"
    exit 1
fi
```

The container will not start if the firewall is misconfigured. That is a deliberate design choice. A broken sandbox is worse than no sandbox because it creates a false sense of security.

## AI Tools as First-Class Citizens

Claude Code and Gemini CLI are installed at the system level during the Docker build, not left for the user to configure after the container starts. Claude Code uses the native installer, and Gemini CLI is installed globally via npm:

```dockerfile
# Install Gemini CLI globally via npm (managed by Volta)
RUN npm install -g @google/gemini-cli

# Install Claude Code using the native installer (npm method is deprecated)
RUN curl -fsSL https://claude.ai/install.sh | bash

# Install GSD (Get Shit Done) for Claude Code and Gemini CLI
RUN npx get-shit-done-cc@latest --all --global
```

**The configuration directories for both tools are mounted as named Docker volumes.** This means API keys, settings, and conversation history survive container rebuilds:

```json
"mounts": [
    "source=claude-code-config-${devcontainerId},target=/home/vscode/.claude,type=volume",
    "source=gemini-cli-config-${devcontainerId},target=/home/vscode/.gemini,type=volume"
]
```

Rebuilding the container does not wipe your Claude Code configuration or force you to re-authenticate. The volumes are scoped to the dev container ID, so different projects get isolated configurations.

GSD (Get Shit Done) is also pre-installed as a workflow layer on top of Claude Code and Gemini CLI. It provides structured project planning, phase execution, and verification patterns for AI-assisted development. Having it baked into the image means the full AI toolchain is ready the moment the container starts.

**The repo also ships custom Claude Code commands in `.claude/commands/`.** The first is a local-only code review command that orchestrates multiple AI agents in parallel to review pull requests:

1. A Haiku agent checks whether the PR should be skipped (closed, draft, or trivial)
2. A second Haiku agent discovers all relevant CLAUDE.md files in the repo
3. A Sonnet agent summarizes the changes
4. Four agents run in parallel: two Sonnet agents audit CLAUDE.md compliance while two Opus agents scan for bugs and logic errors
5. Flagged issues go through a validation pass to eliminate false positives
6. Only high-signal findings make it to the terminal output with suggested fixes

The command is scoped to `gh` CLI tools only and outputs findings to the terminal rather than posting comments on the PR. This keeps code review local and private, which matters when you are iterating on a PR before it is ready for human review. The constraint list is deliberate: no nitpicks, no style concerns, no linter-catchable problems. Only syntax errors, type errors, clear logic failures, and unambiguous CLAUDE.md violations get flagged.

## Developer Experience

The terminal environment is opinionated. **Zsh with Powerlevel10k is the default shell**, configured during the Docker build so there is no manual setup step:

```dockerfile
RUN sh -c "$(wget -O- https://github.com/deluan/zsh-in-docker/releases/download/v${ZSH_IN_DOCKER_VERSION}/zsh-in-docker.sh)" -- \
  -p git \
  -p dotnet \
  -a "export PROMPT_COMMAND='history -a' && export HISTFILE=/commandhistory/.zsh_history" \
  -x
```

Command history is persisted to a named volume at `/commandhistory`, so your shell history survives container rebuilds just like the AI tool configs. Git Delta is installed for readable, syntax-highlighted diffs. Volta manages the Node.js toolchain with pinned versions that stay consistent across rebuilds.

**The vscode user has passwordless sudo.** This is intentional for a development container where the firewall script needs root privileges to manipulate iptables. The sudoers entry is scoped to both general use and the specific firewall script:

```dockerfile
RUN echo "$USERNAME ALL=(ALL) NOPASSWD:ALL" > /etc/sudoers.d/$USERNAME
```

## Container Architecture

The base image is Microsoft's .NET 10 SDK on Ubuntu 24.04. The container requires two Linux capabilities beyond the default set:

```json
"runArgs": [
    "--cap-add=NET_ADMIN",
    "--cap-add=NET_RAW"
]
```

`NET_ADMIN` allows the container to modify iptables rules and create ipsets. `NET_RAW` allows raw socket operations needed by the firewall verification step. Without these capabilities, the iptables firewall would fail silently or crash on startup.

**Docker-in-Docker is enabled through the official dev containers feature**, so you can build and run Docker containers from inside the dev container. This is useful for testing containerized .NET applications without leaving the sandbox.

```json
"features": {
    "ghcr.io/devcontainers/features/docker-in-docker:2": {}
}
```

The `waitFor: "postStartCommand"` setting in `devcontainer.json` ensures the firewall is fully configured before the VS Code terminal becomes available. The editor will not connect until `init-firewall.sh` completes and passes its verification checks. You never work in a container that has not been properly locked down.

Six VS Code extensions are pre-installed: the .NET runtime, C# language support, C# Dev Kit, Claude Code, Docker, and GitLens. These are declared in the container configuration rather than in a user profile, so every team member gets the same tooling without manual setup.
