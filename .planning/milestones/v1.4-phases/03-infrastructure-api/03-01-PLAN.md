<task type="auto">
  <name>Task 2: Create view count route handler with GET, POST, and IP deduplication</name>
  <files>
    src/app/api/views/[slug]/route.ts
  </files>
  <action>
    Create `src/app/api/views/[slug]/route.ts` with the following structure:

    **Route segment config (INFRA-05):**
    ```typescript
    export const dynamic = 'force-dynamic'
    ```
    This MUST be at the top level of the module to prevent Next.js from caching GET responses at build time.

    **Imports:**
    - `{ redis }` from `@/lib/redis`
    - `{ createHash }` from `crypto` (Node.js built-in — NOT `crypto.subtle`)

    **IP hashing helper function:**
    Create a `hashIP(ip: string): string` function using `createHash('sha256').update(ip).digest('hex')`. This is a pure function, not async. Keep it in this file (no need for a separate module).

    **GET handler (INFRA-03):**
    ```typescript
    export async function GET(
      request: Request,
      { params }: { params: Promise<{ slug: string }> }
    ) {
      const { slug } = await params
      // ...
    }
    ```
    - Read view count from Redis: `redis.get<number>(`views:${slug}`)` — returns `null` for new slugs
    - Default to `0` if null: use `?? 0`
    - Return `Response.json({ slug, views })`
    - Wrap in try/catch: on Redis error, `console.error('[views] Redis error:', error)` and return `Response.json({ error: 'Failed to fetch view count' }, { status: 500 })`

    **POST handler (INFRA-02, INFRA-04):**
    ```typescript
    export async function POST(
      request: Request,
      { params }: { params: Promise<{ slug: string }> }
    ) {
      const { slug } = await params
      // ...
    }
    ```
    - Resolve client IP from `x-forwarded-for` header: `request.headers.get('x-forwarded-for')?.split(',')[0]?.trim() ?? '127.0.0.1'`. Take first value only (Vercel anti-spoofing ensures this is the real client IP).
    - Hash the IP with `hashIP(ip)` — NEVER store the raw IP in Redis.
    - Use `redis.pipeline()` for a single HTTP round-trip:
      1. `p.set(`dedup:${slug}:${ipHash}`, '1', { ex: 86400, nx: true })` — set dedup key with 24h TTL, only if not exists (NX). `ex: 86400` = 24 hours in seconds.
      2. `p.incr(`views:${slug}`)` — increment the view counter (auto-initializes to 0 then increments to 1 for new keys).
    - Execute pipeline: `const [dedupResult, viewCount] = await p.exec<[string | null, number]>()`
    - `dedupResult` is `'OK'` if key was set (new visitor), `null` if already existed (repeat visitor within 24h)
    - Return `Response.json({ slug, views: viewCount, deduplicated: dedupResult === null })`
    - Wrap in try/catch: same error pattern as GET.

    **Key design decisions (Claude's discretion per CONTEXT.md):**
    - Response shape: `{ slug, views }` for GET; `{ slug, views, deduplicated }` for POST (the extra field lets Phase 4 client code know if it was a repeat visit)
    - Redis key prefixes: `views:` for counters, `dedup:` for IP dedup keys
    - No slug validation against published posts (harmless orphan keys, Phase 4/5 only displays counts for real slugs)
    - No rate limiting beyond IP dedup (sufficient for personal blog traffic)
    - Pipeline (not transaction) for dedup+increment (negligible race condition risk, simpler code)
    - Fallback IP `127.0.0.1` when header is missing (local dev scenario)

    **Style conventions (per CONVENTIONS.md):**
    - Single quotes for strings
    - 2-space indentation
    - camelCase for functions and variables (`hashIP`, `ipHash`, `viewCount`, `dedupResult`)
    - `import type` not needed here (all imports are runtime values)
    - No barrel files — direct imports from `@/lib/redis`
